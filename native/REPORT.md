# Native Physics Lab 0.10.6 (alpha) — stage 9 report: the jump sameness test made portable

The Windows CI run of stage 8 (commit 0941725, run 37189309944) failed: `atom_physics` 18203 checks, 7 failed. The same code passes on Linux GCC. Only a test was changed (plus one inline helper, below); the stage 8 speed work is unchanged. `index.html` untouched (sha256 e5501387ae64…).

## What I established about the cause
- **The failing checks, from the CI log** (read through the GitHub tools): exactly the 7 byte-hash checks of `testJumpSameDots`: "the new dots, the amplitudes and the walker are the same, bit for bit" (4f, 2p, 2s) and "the cloud after landing … is the same" (4f, 2p, 3d reduced motion, 2s). The checks that hashed the colour groups (Sign, Wheel), the random numbers and the dot count **passed on Windows** for the same four jumps.
- **What differs between the two sets:** the failing hashes contain the raw bytes of the walker (`w2` in the first, `w` in the second): three doubles at the end of a chain of 48,800 steps built with `log`, `cos`, `sqrt` (the Gaussian step). The passing ones are made of integers (random numbers, counts) or of colour numbers derived from floats. The 3d reduced-motion case has no first hash (its arrays are cleared at once) and failed only in the second: this matches 3 + 4 = 7.
- **Sensitivity check (Linux, probe):** one unit in the last place in `w2.x` changes the walker's byte hash, while `float(w.x · a0)`, the number actually stored for the dot, stays the same. So a last-bit difference between GCC's and MSVC's C libraries (allowed by both) would fail these hashes and nothing else.
- **Would stage 7's code have failed too?** Argued, not run (no Windows here): the fingerprints were recorded from stage 7's code and hashed the same walker bytes, produced by the same `gauss` (`log`, `cos`) in `walk()`; the new code does the same arithmetic. So a stage 7 build would have been compared with the same recorded bytes and failed the same way, the test being new in stage 8. I could not prove which side of the compilers is "right" for the last bit, and it does not matter: neither is wrong.
- **Not a bug in the speed work:** the four jumps passed everything that does not hash raw doubles on Windows, including the existing jump tests, `testJumpBuild` (new against old inside one run, 22 checks) and the old dot hashes. The Windows log also shows `benchmark.cpp` and `atom_view.cpp` (never compiled in the cloud) **compiled** on MSVC.

## What the test does now (`testJumpSameDots`, 4 jumps: 4f→3d Ultra 48,000, 2p absorb →3d, 3d→2p reduced motion, 2s→1s)
1. **Old way against new way, same run, bit for bit** (right here, because one compiler computes both): `oldJumpBuild` is stage 7's `beginTransition` and `walk()` written out in the test (4 `psi` evaluations per new dot, the global generator, all at once). It is run from the same state (the generator put back to where the jump began; for the absorbed photon, the old dots and the generator are taken at the frame the jump begins) and compared with the new build: the new dots, both amplitude arrays, the walker, the generator's end state (the same count of random numbers), and, for the instant jump, the cloud it leaves (dots, signs, walker). Also the whole run to the end, built over the frames against built at once: dots, signs, phases, walker, count and generator after landing, bit for bit.
2. **Recorded Linux numbers with tolerances, not bytes** (like the stage 2 dot tests): dot count, the walker at the end of the build and after landing, sums of |dot coordinates|, |amplitudes| and phases, how many dots are shown at 0.3 and 0.7 of the jump, a colour-number sum, the dots in the cloud and the next three random numbers. Tolerances: float sums 1e-6 relative (a float holds 6e-8; a library difference of 1e-16 in a double, maybe 1e-14 after 48,800 chained steps, moves a stored float by one last place only rarely, at most about 1e-7 of a sum; 1e-6 is 10 times that); the walker 1e-9 (accumulated difference about 1e-14); shown-dot counts 0.05 % of all dots + 1 (a dot on the edge of its odds may flip); the count and the random numbers exactly (integer maths and an exact division). These are reasoned guards, not measured on Windows: no Windows run of the numbers existed before this stage's CI run (below).
3. `jumpPhaseOf(A, B, T)` (new inline in `atom_core.h`, the same expression `jumpGroups` used, now called by it): tested bit for bit against the old per-dot expression on 20,000 random cases. Why: see the experiment, P1.
`testJumpBuild` had no raw-byte or recorded comparison (everything is new against old in one run, or integers), and passed on Windows: no change needed.

## Proof it still catches a real change (temporary perturbations, each reverted; full atom run each time)
- **P1, one term reordered** in the phase expression, `T.sth * B * T.em` → `T.sth * (B * T.em)`: the first version of the new test did **not** fail (a last-bit change of the phase almost never flips a colour group; the old test did not catch it either). So I added the `jumpPhaseOf` comparison; with it P1 fails ("jumpPhaseOf … same bits as the old per-dot expression"), 1 failed.
- **P2, the chain's step size 1e-9 too large:** fails the three old-against-new checks of the 4f jump (and others), and the recorded walker (got −0.61042645122… want −0.61042645026…, 1.6e-9 relative: above the 1e-9 tolerance).
- **P3, the carried wave function not updated on an accepted step:** fails the old-against-new checks and the recorded sums.
Each was reverted (`git diff` empty for the perturbed lines) and the suite re-run clean.
